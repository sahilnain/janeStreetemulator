## How it works

The Protocol Emulator is a small programmable I/O processor. It speaks UART, SPI (master and slave, 3-wire, any word size), I2C (master, slave, multi-master, 10-bit, Hs) and USB low and full speed (device or host, at transaction level) on its 8 bidirectional pins. No block is specific to any of these protocols: each protocol is a program.

The work is split in two:

- **Hardware units put the bits on the wires.** A TX unit and an RX unit send or receive one packet of 1–16 bits per start, with exact timing. Their options are generic: a clock pin (CPOL, CPHA, clock stretching), an external clock, majority voting, NRZI, bit stuffing, a differential pair, end-of-packet, and back-to-back bytes. Two event detectors start or stop a unit on a pin condition in the same cycle (a UART start bit, a USB end of packet, an I2C START), and a CRC unit checks or appends a CRC with any polynomial.
- **A small controller runs the protocol rules in firmware.** It executes one 29-bit instruction per cycle (21 ns at 48 MHz) from a 162-word program memory, with eight 16-bit registers, and acts between packets: START, STOP, ACK, error checks, deciding what to answer.

The host microcontroller talks to the chip over a 4-bit handshaked bus and an IRQ pin. It loads the firmware, then exchanges data in three ways:

| Path | Size | Use |
|---|---|---|
| TX and RX FIFOs | 8 bytes each | byte streams (UART, SPI slave) |
| Mailbox | 8 registers × 16 bits | requests and results: counts, addresses, status |
| Data memory | 256 bytes, an IHP SRAM macro | payload: bytes to send from address 0x00, received bytes at 0x80 |

Two data movers copy payload between the data memory and the FIFOs by themselves, so the firmware only starts them and checks when they are done.

### The host bus

| Pin | Use |
|---|---|
| `ui[3:0]` | data nibble in |
| `ui[5:4]` | operation: 0 ADDR, 1 WRITE, 2 READ, 3 SYNC |
| `ui[6]` | strobe: toggle it to perform the operation |
| `uo[3:0]` | data nibble out |
| `uo[4]` | ack: toggles when the operation is done |
| `uo[5]` | IRQ |

Each operation takes one nibble: set the operation and the nibble, toggle the strobe, and wait for ack to toggle. The bus is asynchronous, so the host can be much slower than the chip.

- **Address:** two ADDR operations, high nibble first.
- **Write:** two WRITE operations, high nibble first; the second one performs the write.
- **Read:** two READ operations; the first fetches the byte and returns the high nibble, the second returns the low nibble.
- **SYNC** resets the nibble phase if the host loses track.

The address does not increment, so a FIFO can be read or written repeatedly with data operations only.

### Main registers

| Address | Name | Use |
|---|---|---|
| 0x00 | ID | reads 0x50 |
| 0x01 | VERSION | reads 0x03 |
| 0x02 | RUN | bit 0: the controller runs |
| 0x03 | RESTART | write 1: restart the controller from START_PC |
| 0x04 | STATUS | FIFO flags and errors |
| 0x06 | IRQ_EN | IRQ sources: RX FIFO not empty, TX FIFO not full, errors, firmware IRQ |
| 0x08 / 0x09 | TXF_DATA / RXF_DATA | push to the TX FIFO / pop from the RX FIFO |
| 0x0A, 0x10–0x13 | IMEM_ADDR, IMEM_DATA | load a firmware word: 4 bytes, low first; writing 0x13 stores it |
| 0x0F | DOORBELL | any write tells the firmware a request is ready |
| 0x14–0x1B | PIN_OD, PIN_FILT, PIN_OWNER | open drain, input filter, and which unit owns each pin |
| 0x20–0x21 | START_PC | where RESTART starts |
| 0x28 / 0x29 | DMEM_ADDR / DMEM_DATA | data memory access, the address advances after each byte |
| 0x30–0x3F | MBOX | mailbox M0–M7, M[i] low byte at 0x30 + 2i |

The full register map, the instruction set and every program are described in `docs/architecture_guide.md` in the project repository.

## How to test

You need a host that can drive 7 inputs and read 6 outputs, for example the RP2040 on the Tiny Tapeout demo board. The clock is 48 MHz.

1. Reset the chip. Read ID (0x00): it must be 0x50. VERSION (0x01) must be 0x03.
2. Write RUN = 0, then load a program: IMEM_ADDR = 0, then 4 bytes per word to 0x10–0x13.
3. Set PIN_OD, PIN_FILT and PIN_OWNER for the protocol, then START_PC = 0, RESTART = 1 and RUN = 1.
4. Use the protocol. The programs are generated by `test/common/pe_fw.py` in the repository (for example `pe_fw.uart(B=417)` for 115200 baud).

A first test that needs only a wire: load the UART program with TX on P0 and RX on P1, connect P0 to P1, write bytes to TXF_DATA (0x08) and read them back from RXF_DATA (0x09).

For a request-driven program (SPI master, I2C master, USB), write the request into the mailbox and the payload into the data memory, write DOORBELL, wait for the IRQ, then read the result from the mailbox and the received bytes from the data memory at 0x80.

## External hardware

None for UART or SPI. I2C needs pull-up resistors on SCL and SDA (the pins are open drain). USB needs the usual series resistors and pull-up (D− for low speed, D+ for full speed), and a 3.3 V level shifter or transceiver.
